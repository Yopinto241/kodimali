# Agent registration location and public error messages

A confirmed website signup bug submitted a district ID as `location_id`. The deployed `guard_agent_location_hierarchy` function accepts only an active area connected to ward, district and region. The deployed `handle_auth_user_created` inserts the metadata location directly into the agent row; rejection aborts signup and rolls back the auth user/profile. This explains a reproducible server-error path. The individual failed request for `frankjoachim390@gmail.com` was not available, so it cannot be conclusively attributed to this bug. A read-only production check found no auth user for that address at the start of the investigation.

Web self-registration now uses the area hierarchy selector already used for protected agent creation. Submit remains disabled until an area is selected, and the JSON metadata sends that area ID. Correct database validation and admin approval requirements are preserved; no database migration is needed. No real customer account was created, changed, promoted or deleted during testing.

Web self-registration and staff creation show application-owned, translated messages for known validation errors and a polite fallback for unknown/server/database failures. Thrown network failures are caught and the submit button recovers. Manage mobile registration applies the same policy to signup, options loading, username checks and location loading. The existing login messages and approval rules are preserved. No APK is generated.

Verification: `scripts/test-agent-registration.sql` uses an isolated local fixture to reproduce transactional rollback for a district, then creates a pending/inactive agent with a valid area, primary category and customer role. Browser fixtures intercept signup requests: area is required, exact area metadata is checked, server errors do not expose SQL details, duplicate messages are actionable, and success works at 390px in English/Swahili and 1440px in English. All 21 web library tests, ESLint and the production build passed. Nine targeted Manage mobile tests passed with one test worker (registration errors, login readability and supervisor controls); analysis reported no issues. A parallel mobile test attempt ran out of host memory; the serial rerun passed. Evidence is in `tmp/agent-registration-*.log`.
